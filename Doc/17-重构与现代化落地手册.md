# 17 · 重构与现代化落地手册

> FlamePanel 后端重构 + 前端现代化/修复的统一落地手册（Coding Agent 可执行版）
>
> 本文档由三份权威方案合并而来，作为**唯一可执行落地手册**：
> 1. 《FlamePanel-Backend-Refactor-Playbook》—— 后端安全加固、六边形架构纯度提升、工程化与长期维护
> 2. 《FlamePanel-Frontend-Fix-Plan》—— 前端稳定性、数据层、设计系统、a11y、工程化修复
> 3. 《FlamePanel-Frontend-OpenVue-Modernization》—— OpenVue 体系下的现代化体验与可维护 API 契约

> **原则**：小步可回滚、功能不破坏、文档与代码同步、每阶段有明确验收标准。
> **禁止**：跳过阶段 0 直接做大规模重构；在 domain 引入 sqlx/axum/bollard；Handler 直接访问 Repository；业务视图直接散落裸 OpenVue 组件 / 硬编码色值。

## 第一部分 · 后端重构与长期维护

> **适用范围**：`flame-kernel` 全部后端代码。

### 1. 项目现状速览（只读，不改代码）

#### 1.1 目录与分层（当前）

```
flame-kernel/src/
├── domain/          # entity.rs + error.rs + repository.rs（端口，零外部依赖）
├── application/     # service.rs, app_store_service.rs, app_store_ports.rs, ...
├── infrastructure/  # factory.rs, sqlite.rs, db.rs, docker.rs, db_models.rs, app_store/, ...
├── api/             # routes, middleware, handler/*, types.rs, openapi.rs
├── runtime/         # supervisor.rs（TaskSupervisor）+ request_id.rs（Stage2）
├── core/            # error.rs (AppError + ErrorCode)
├── event/           # EventBus
├── plugin/          # wasmtime 沙箱
├── webserver/       # 5 引擎配置生成
├── database/        # MySQL/Redis 原生管理
├── resilience/      # Circuit Breaker + Retry
├── terminal/        # Web 终端
├── file/            # 文件服务（路径沙箱）
├── notification/    # 邮件通知
├── utils/           # JWT / bcrypt
├── lib.rs           # FlameKernel 组合根 + 后台任务编排
└── main.rs
```

#### 1.2 核心问题清单（必须解决）

| ID | 问题 | 严重度 | 阶段 |
|----|------|--------|------|
| S1 | 默认 root 运行 + 终端/文件路径风险 | P0 | Stage0 |
| S2 | JWT 无强制轮换 / access+refresh 不完整 | P0 | Stage0 |
| S3 | WASM 资源限制与签名不足 | P0 | Stage0 |
| A1 | 实体带 `FromRow`，领域依赖 sqlx | P1 | Stage1 |
| A2 | Application 直接依赖 infrastructure::app_store 细节 | P1 | Stage1 |
| A3 | DockerRepository 等过胖端口 | P1 | Stage1 |
| A4 | 贫血模型，领域行为不足 | P1 | Stage1 |
| C1 | 组合根臃肿，后台任务无统一取消 | P2 | Stage2 |
| C2 | 分页全量加载 | P2 | Stage2 |
| E1 | Axum 过时、无 feature flags、无 OpenAPI | P3 | Stage3 |

#### 1.3 优点（重构时必须保留）

- 依赖方向大体正确：domain 定义端口，infrastructure 实现，application 编排，api 为驱动适配器。
- `RepoFactory` + InMemory/SQLite 双后端，利于测试。
- 统一 `AppError` + 稳定 `ErrorCode`，对外 `{code, error, message}`。
- 认证 + RBAC 合并中间件（一次 JWT + 一次查库）。
- Docker 不可用时降级、Circuit Breaker、事件总线骨架、应用商店三格式/三模式编排。
- CI：fmt、clippy `-D warnings`、全量测试；文档体系完整（`Doc/`）。

### 2. 全局约束（所有阶段必须遵守）

1. **依赖方向**：`api → application → domain`；`infrastructure` 只实现 domain 端口；**禁止** application 直接 `use crate::infrastructure::具体类型`（除组合根外）。
2. **错误**：对外统一 `{code, error, message}`；稳定 ErrorCode 不随意删除；内部错误记 source 链。
3. **测试**：每完成一个子任务必须 `cargo test --all` 通过；涉及 API 的保持现有集成测试绿。
4. **迁移**：SQLite 变更必须幂等；优先复用已有 `add_column_if_missing` 风格。
5. **文档同步**：改公共行为时更新 `Doc/01-架构设计.md`、`Doc/05-后端开发指南.md`、`Doc/06-部署运维指南.md`。
6. **提交粒度**：每个子任务独立 commit，message 前缀：`security:` / `refactor:` / `feat:` / `chore:`。

### 3. 阶段 0：安全与运行时加固（P0，必须先完成）

**目标**：消除最严重安全风险，服务可非 root 运行，终端/文件有沙箱，JWT/WASM 基线达标。

#### 3.1 非 root 运行与 capabilities

**涉及文件**：`install.sh`、`uninstall.sh`、systemd unit 模板、`Doc/06-部署运维指南.md`

**动作**：

1. 创建系统用户与组：`flamepanel`（无登录 shell）。
2. 目录权限：
   - `/opt/flamepanel` 属主 `flamepanel:flamepanel`
   - 数据/日志目录 `750`
   - `flamepanel.env` `600`
3. systemd 示例（写入 install.sh 生成逻辑）：

```ini
[Service]
User=flamepanel
Group=flamepanel
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/flamepanel/data /opt/flamepanel/logs
# 若必须操作 docker.sock / 部分系统服务，再按最小原则加 Capability 或 sudoers 白名单
```

4. 需要 root 的操作（包安装、nginx 重载、防火墙）改为：
   - 优先 `CapabilityBoundingSet` / `AmbientCapabilities`，或
   - 受控的 `sudo -n` 白名单命令（文档明确列出）。

**验收**：

- [ ] 安装后 `ps` 显示进程用户为 `flamepanel`
- [ ] 核心 API（登录、列表容器、读设置）正常
- [ ] 文档已说明非 root 限制与特权操作清单

#### 3.2 终端与文件路径沙箱

**涉及文件**：`flame-kernel/src/terminal/`、`flame-kernel/src/file/`、相关测试

**动作**：

1. 终端启动时：
   - 强制 `cwd` 为允许目录（如用户家目录或配置的 `workspace_root`）
   - 清理危险环境变量（`LD_PRELOAD` 等）
2. 文件 API：
   - 所有路径规范化（`canonicalize`）后必须落在白名单根目录下
   - 拒绝 `..` 穿越与指向白名单外的符号链接
   - 写操作二次校验
3. 配置项：`OP_FILE_ROOT` / `OP_TERMINAL_CWD`（默认安全值）

**验收**：

- [ ] 无法通过 API 读取 `/etc/shadow`、`/root`
- [ ] 终端无法 `cd` 到白名单外
- [ ] 现有文件/终端集成测试通过或新增对应否定用例

#### 3.3 JWT 强化

**涉及文件**：`flame-kernel/src/utils/`（jwt）、`api/handler/auth/`、`config/`、application 会话相关

**动作**：

1. 启动时校验 `jwt_secret` 长度 ≥ 32，否则拒绝启动并明确日志。
2. 实现：
   - Access Token：短过期（如 15–60 分钟）
   - Refresh Token：长过期，可存储/轮换
3. 提供密钥轮换接口（admin only）：更新 secret 后旧 access 策略文档化（黑名单或短宽限期）。
4. 登录失败锁定逻辑保持（已有则对齐文档）。

**验收**：

- [ ] secret 过短时进程拒绝启动
- [ ] access 过期后 refresh 可换新；轮换后旧 token 策略符合文档
- [ ] 现有登录/鉴权测试更新并通过

#### 3.4 WASM 资源限制与完整性

**涉及文件**：`flame-kernel/src/plugin/sandbox.rs`、`application/app_store_service.rs` WASM 安装路径

**动作**：

1. 每个插件执行设置：
   - memory limit（可配置，有默认上限）
   - timeout / fuel（wasmtime 能力）
2. 安装/恢复时校验 `wasm_hash`（已有字段则强制比对）。
3. 失败时返回稳定错误码，不泄漏内部路径。

**验收**：

- [ ] 超时/超内存插件被终止且不影响主进程
- [ ] hash 不匹配拒绝加载
- [ ] 相关单元/集成测试通过

#### 3.5 SQLite 运行时加固

**涉及文件**：`infrastructure/factory.rs` 或 sqlite 连接处、迁移/启动逻辑

**动作**：

连接后执行：

```sql
PRAGMA journal_mode=WAL;
PRAGMA busy_timeout=5000;
PRAGMA synchronous=NORMAL;
```

（按项目现有 sqlx 用法写入）

**验收**：

- [ ] 启动日志或测试可确认 WAL
- [ ] 并发写简单压测不出现大量 `database is locked` 直接崩溃

#### 阶段 0 完成标准

- [ ] 上述 3.1–3.5 全部勾选
- [ ] `cargo test --all` 绿
- [ ] `install.sh` 与部署文档已更新
- [ ] 记入 CHANGELOG：`security: stage0 hardening`

### 4. 阶段 1：领域纯度与端口治理（P1）

**目标**：domain 零 sqlx/axum；端口按职责拆分；application 只依赖端口；领域行为上移。

#### 4.1 错误类型拆分

**涉及文件**：新建 `domain/error.rs`、`core/error.rs`、domain/application 边界

**动作**：

1. `DomainError`：纯业务（NotFound、Validation、Conflict、Forbidden 业务语义等），**不**依赖 axum。
2. `AppError` 保留 HTTP 映射，实现 `From<DomainError>`。
3. Repository trait 可改为返回 `Result<T, DomainError>`，或继续 AppError 但内部转换清晰（推荐逐步迁到 DomainError）。
4. 更新 `IntoResponse` 仅在 api/core 层。

**验收**：

- [ ] `domain` 模块编译不依赖 `axum`
- [ ] 对外 JSON 错误格式不变

#### 4.2 去掉实体上的 FromRow

**涉及文件**：`domain/entity.rs`、新建 `infrastructure/db_models.rs`、`infrastructure/sqlite.rs`、`db.rs`

**动作**：

1. 将所有 `#[derive(..., FromRow)]` 的持久化结构移到 infrastructure。
2. domain 实体只保留业务字段 + 少量方法（见 4.4）。
3. 在 sqlite/inmemory 实现中做 `DbUser ↔ User` 映射（函数或 `From`/`TryFrom`）。
4. 确保 Serialize 给前端的 DTO 仍在 api 层或显式转换，避免把 `password_hash` 等泄漏（审查现有 handler）。

**验收**：

- [ ] `rg "FromRow" flame-kernel/src/domain` 无结果
- [ ] 全量测试通过

#### 4.3 拆分 DockerRepository（模板，可推广）

**目标端口**（可按项目命名微调）：

```text
ContainerRepository
NetworkRepository
VolumeRepository
ImageRepository
ComposeRepository
```

**动作**：

1. 在 `domain/repository.rs` 定义上述 trait，方法从原 trait 迁出。
2. `infrastructure/docker.rs` / InMemory 实现分别实现新 trait。
3. `RepoFactory` 增加 `create_container_repo` 等，或返回聚合结构体。
4. `DockerService` 改为持有多个 `Arc<dyn ...>` 或一个门面，对外 API 方法签名尽量保持不变（减少 handler 改动）。
5. 删除或 `#[deprecated]` 旧巨型 trait，最终移除。

**验收**：

- [ ] 原 Docker 相关 API 行为不变
- [ ] 可为单个小端口写 mock 测试

**同类任务（同阶段或紧随）**：评估 `WebServerRepository`、`DatabaseRepository` 是否按引擎/类型拆分（能拆则拆，不能则文档说明边界）。

#### 4.4 领域行为上移（去贫血）

**示例（必须落地若干，形成模式）**：

```rust
// domain
impl User {
    pub fn ensure_can_change_password(&self) -> Result<(), DomainError> { ... }
    pub fn mark_password_changed(&mut self);
}

impl ServerNode {
    pub fn is_online(&self, now: DateTime<Utc>, timeout_secs: i64) -> bool; // 已有则保留
}

impl InstalledApp {
    pub fn can_upgrade_to(&self, target_version: &str) -> Result<(), DomainError>;
}
```

Service 中调用实体方法，而不是散落 if。

**验收**：

- [ ] 至少 User / InstalledApp / ServerNode 有有意义的领域方法
- [ ] Service 单测覆盖这些分支

#### 4.5 切断 Application → Infrastructure 直接依赖

**重灾区**：`application/app_store_service.rs`

**动作**：

1. 在 domain（或 application 端口模块）定义：
   - `AppPackageAdapter`（parse_metadata / parse_version）
   - `ComposeSecurityScanner` / `VariableMapperPort`（或合并为安装编排端口）
2. 现有 `FlameAdapter` / `OnePanelAdapter` / `BaotaAdapter` / `select_adapter` / `VariableMapper` / `scan_compose` 实现这些端口，仍放在 `infrastructure/app_store/`。
3. `AppStoreService::new` 注入 `Arc<dyn ...>`，**删除** application 内对 `crate::infrastructure::app_store::...` 的直接 use（组合根组装除外）。
4. `FlameKernel::build_services` 负责创建具体适配器并注入。

**验收**：

- [ ] `rg "infrastructure::app_store" flame-kernel/src/application` 仅剩注释或为零
- [ ] 应用商店安装/导入相关测试通过

#### 阶段 1 完成标准

- [ ] domain 不依赖 sqlx、axum、bollard
- [ ] Docker 端口已拆分且 API 兼容
- [ ] AppStore 适配器经端口注入
- [ ] `cargo test --all` 绿
- [ ] 更新 `Doc/01-架构设计.md` 依赖规则与端口列表

### 5. 阶段 2：组合根、生命周期与可观测性（P2）

#### 5.1 后台任务 Supervisor

**涉及文件**：新建 `flame-kernel/src/runtime/supervisor.rs`、`lib.rs` 中所有 `tokio::spawn`

**动作**：

1. 实现带 `CancellationToken` + `JoinSet` 的 Supervisor。
2. metrics 采集、自动备份、节点离线扫描、定时任务 tick 全部经 Supervisor 启动。
3. `shutdown_signal` 触发 `cancel` 并 `join`（设超时）。

**验收**：

- [ ] Ctrl+C / SIGTERM 后后台任务可退出，无长期僵尸任务
- [ ] 测试或手动验证关闭日志

#### 5.2 Request-Id 与 tracing

**涉及文件**：`api/middleware.rs`、tracing 初始化（main/lib）

**动作**：

1. 中间件生成/传播 `x-request-id`。
2. 日志字段包含 `request_id`、`user_id`（若有）。
3. 生产默认支持 JSON 日志（已有开关则对齐文档）。

**验收**：

- [ ] 响应头带回 request-id
- [ ] 同一请求日志可串联

#### 5.3 分页下沉

**动作**：

1. Repository 增加 `list_page(offset, limit)` 或 cursor 接口（按表选择）。
2. Service 的 `list_*_paginated` 改为调用分页查询，**禁止**先 `list_all` 再 `paginate_slice`（小表可暂留，大表必须改：operation_logs、logs、containers 等）。

**验收**：

- [ ] 大数据量路径不再全表加载（代码审查 + 必要时基准）

#### 5.4 AppState 瘦身（渐进）

**动作**：

- 短期：Builder 或模块化组装减少 `build_services` 样板。
- 中期：按限界上下文拆 State（Auth / Docker / AppStore），Axum 可多 State；不强制一次做完。

**验收**：

- [ ] 新增一个 Service 的修改点 ≤ 3 处（factory + build + state 字段），并在文档中写明步骤

### 6. 阶段 3：工程化（P3，可与功能迭代并行）

#### 6.1 依赖与 Feature Flags

**文件**：`flame-kernel/Cargo.toml`

```toml

default = ["sqlite", "docker", "wasm", "email"]
sqlite = ["sqlx"]
docker = ["bollard"]
wasm = ["wasmtime"]

```

代码用 `#[cfg(feature = "...")]` 隔离可选路径；CI 至少编 default + 全 feature + 裁剪组合。

#### 6.2 升级 Axum

- 升级到当前稳定版 0.8（以升级时 crates.io 为准）。
- 迁移 `Server`、中间件、extractor API。
- 全量测试 + 手工冒烟登录/WS/Docker。

#### 6.3 OpenAPI

- 引入 `utoipa`（或等价）。
- 关键路由与 DTO 注解。
- CI 生成 `openapi.json`；前端可后续用 openapi-typescript 生成类型。

#### 6.4 权限映射可维护性

- 将 `route_permission` 巨大 match 改为声明式表（常量数组 / phf / 路由挂载时注册）。
- 新增 handler 的 checklist：必须注册权限。

#### 6.5 CI 增强

在现有 fmt/clippy/test 上增加：

- `cargo audit`
- `cargo deny`（可选）
- feature 组合编译

### 7. 日常开发强制规范（给 Agent 的操作清单）

#### 7.1 新增业务模块标准流程

1. **Domain**：实体、枚举、`Repository` trait、领域方法、`DomainError` 变体（如需）。
2. **Infrastructure**：InMemory + Sqlite 实现、migration、`RepoFactory` 注册。
3. **Application**：Service，**只**依赖 `Arc<dyn Trait>` 与 EventBus。
4. **API**：DTO、handler、`routes()`、权限注册、审计（写操作默认走中间件）。
5. **测试**：Service 单测 + 至少一条集成测试。
6. **文档**：API 文档 + 权限表 + 架构（若新边界）。

#### 7.2 PR / 提交前自检

```text
[ ] 依赖方向正确
[ ] 无 Handler → Repository 直访
[ ] 无 application → infrastructure 具体类型
[ ] 错误码稳定且前端可映射
[ ] 写操作可被审计
[ ] cargo test --all
[ ] cargo clippy --all-targets -- -D warnings
[ ] 文档已更新（若对外行为变化）
```

#### 7.3 禁止清单

- 在 `domain/` 使用 `sqlx::FromRow`、`axum`、`bollard`
- 新增过胖 God Repository
- 全量 `list` 后内存分页（大数据表）
- 无 CancellationToken 的长期 `tokio::spawn` 后台循环（阶段 2 后）
- 默认 root 部署文档回退

## 第二部分 · 前端修复方案（Fix-Plan）

> **依据**：此前前端专业评审（设计系统、信息架构、工程化、可访问性、性能）。
> **目标**：在不大改产品定位的前提下，系统性修复体验、一致性、性能与可维护性问题。
> **原则**：小步可回滚、与后端错误码/API 对齐、优先用户可感知问题、每阶段可验收。
> **技术栈现状**：Vue 3.5 + TypeScript + OpenVue 0.7 beta + UnoCSS + Pinia + Vue Router + vue-i18n + ECharts + xterm.js + Axios + Vite 8。

### 8. 问题对照与优先级

| ID | 问题 | 用户/工程影响 | 优先级 |
|----|------|---------------|--------|
| F1 | 设计系统不完整：令牌/封装层薄、玻璃态可读性与性能风险 | 视觉不一致、低端机卡顿、对比度不足 | P0 |
| F2 | 无统一数据层：轮询 + WebSocket 混用、状态易不一致 | 列表抖动、重复请求、关闭页后仍请求 | P0 |
| F3 | keep-alive / 多页签 / 图表 / 终端销毁不完整 | 内存泄漏、长时间使用变慢 | P0 |
| F4 | Loading / Error / Empty 状态不统一 | 操作反馈差、错误难懂 | P0 |
| F5 | 大列表无虚拟滚动（Docker / 文件 / 日志等） | 数据多时卡顿 | P1 |
| F6 | a11y 弱：命令面板、表格、焦点、ARIA | 键盘用户与无障碍访问受损 | P1 |
| F7 | API 类型手写，与后端易漂移 | 运行时错误、联调成本高 | P1 |
| F8 | 信息架构过载：侧栏功能多、缺角色化/渐进披露 | 新手与 viewer 压迫感强 | P2 |
| F9 | 响应式/平板场景弱 | 非桌面场景可用性差 | P2 |
| F10 | 无 Storybook / 组件回归 | 设计令牌与 Fp* 难维护 | P2 |

## 第三部分 · 前端现代化方案（OpenVue 专属）

> **定位**：在 **OpenVue** 唯一组件体系上，打造现代运维面板的操作感与美观度。
> **关键词**：交互简要、充分便利、可自定义高、可维护高、API 文档清晰。
> **约束**：不引入第二套重型 UI 库；业务层只消费 `Fp*` 封装 + 设计令牌；OpenVue 为底层实现。

### 15. 目标与原则

#### 15.1 产品目标

| 维度 | 目标表现 |
|------|----------|
| 操作感 | 运维高频路径 ≤3 步完成；危险操作有确认但仍顺手；键盘与鼠标同等一等公民 |
| 美观感 | 暗色优先、火焰品牌可辨、密度可控、玻璃仅用于浮动层、无模板化堆砌 |
| 交互感 | 每一步有即时反馈（hover/active/loading/toast）；动效克制、服务反馈而非表演 |
| 便利性 | ⌘K 全局入口、多页签保状态、常用应用/命令、错误可一键重试 |
| 可自定义 | 主题/密度/玻璃/侧栏/背景/语言均可配置，支持导入导出 |
| 可维护 | Fp* 唯一入口、令牌驱动、类型清晰、组件 API 有文档 |
| API 文档 | Fp 组件 props/events/slots 文档 + 前端 api 模块说明 + 与后端错误码对照 |

#### 15.2 设计拨盘（保持）

- **视觉变化**：中高（有辨识度，不花哨）
- **动效强度**：低中（150–300ms，`transform`/`opacity`）
- **信息密度**：高（运维刚需，可用密度档位调节）

#### 15.3 硬性规则

1. **UI 库 = OpenVue**（`openvue` + `@openvue/themes` + `@openvue/openicons`）。
2. **业务视图禁止直接散落使用底层 OpenVue 组件**（例外须在文档登记）；统一经 `components/ui/Fp*`。
3. **样式只走 `--fp-*` 令牌** 与 OpenVue 预设桥接（`flame-preset`），禁止业务内硬编码色值。
4. **图标单一来源**：`@openvue/openicons`，不混用其他图标集。
5. **交互路径尽量短**：列表 → 操作 → Toast/行内结果；复杂流程用分步 Modal，不堆嵌套抽屉。

### 16. 架构分层（可维护核心）

```text
views/*                    # 页面：编排，无样式魔法、无裸 OpenVue
  ↓
components/layout/*        # 壳：Sidebar / Header / Tabs / CommandPalette
components/ui/Fp*          # 设计系统公共 API（对外唯一组件契约）
  ↓
openvue + openicons        # 底层实现
theme/tokens.css           # --fp-* 语义令牌
theme/flame-preset.ts      # 映射到 OpenVue --p-*
theme/glass.css            # 浮动层材质
composables/*              # useTheme / useTableQuery / useCommand / useECharts
api/*                      # 后端 HTTP，错误码归一
```

**维护约定**：改视觉 → 改令牌或 Fp*；改交互模式 → 改 composable；改接口 → 改 `api/` + types。

### 17. OpenVue 使用规范

#### 17.1 允许的底层能力（在 Fp 内使用）

| 能力 | OpenVue | Fp 封装 |
|------|---------|---------|
| 按钮 | `Button` | `FpButton`（含 loading/危险变体） |
| 表格 | `DataTable` + `Column` + virtualScroller | `FpTable` |
| 输入 | `InputText` / `Textarea` / `Password` | `FpInput` |
| 选择 | `Select` | `FpSelect` |
| 对话框 | `Dialog` | `FpModal` |
| 抽屉 | `Drawer` | 可直接或 `FpDrawer` |
| 反馈 | `useToast` / `useConfirm` | `FpToast` / `FpConfirm` |
| 标签 | `Tag` | `FpTag` |
| 空态 | 自绘 | `FpEmpty` |
| 分页 | `Paginator` | 并入 `FpTable` |
| 菜单/命令 | `Menu` 等 | 布局内封装 |
| 提示 | `v-tooltip` | 全局统一 delay |

#### 17.2 封装原则（Fp* API 设计）

```text
Fp 组件 = OpenVue 能力 + 默认设计系统约束 + 透传其余 props
```

- **默认值**：尺寸、圆角、语义色、空态文案走 i18n。
- **透传**：`$attrs` / 明确 `v-bind="$attrs"`，不锁死高级能力。
- **事件**：沿用 Vue 习惯 `update:modelValue`、`click`、`row-select` 等，文档写清。
- **插槽**：`empty`、`loading`、`actions`、`header` 等保持稳定名称。
- **无障碍**：焦点环、`aria-*` 在 Fp 层补齐，业务少操心。

#### 17.3 禁止

- 在 `views/` 同时使用 Element 遗留 API 与 OpenVue。
- 为“好看”在页面写一套独立 CSS 覆盖 OpenVue 内部类名（易碎）；应改 preset/tokens。
- 玻璃用在侧栏长列表与大表格背景（性能与可读性双杀）。

### 18. 现代化操作感（交互简要 + 便利）

#### 18.1 全局交互骨架

| 入口 | 行为 | 说明 |
|------|------|------|
| ⌘K / Ctrl+K | 命令面板 | 搜菜单、跳转、已注册命令（重启容器等） |
| 多页签 | 访问即开、可关、右键批量关 | keep-alive 白名单；重资源页可排除 |
| 顶栏 | 状态灯（节点/WS）、快捷应用、通知、用户 | 一屏掌握健康度 |
| 侧栏 | 分组 + 可折叠 + 设置显隐 | 按角色默认折叠次要组 |
| 右下 Toast | 成功/失败 | 3–5s；错误可带「重试」若传入回调 |
| 危险操作 | FpConfirm | 主按钮危险色；文案短、后果明确 |

#### 18.2 标准页面范式（减少思考）

**A. 资源列表页（Docker / Users / Logs…）**

```text
[标题 + 主操作按钮]
[筛选条：搜索 / 状态下拉 / 刷新]
[FpTable：loading 骨架 | 数据 | empty]
[行操作：最多 3 个显式按钮，其余进「更多」]
```

**B. 详情/编辑**

```text
Modal 或 右侧 Drawer（二选一，同模块统一）
表单 FpInput/FpSelect + 行内错误
底栏：取消 + 主按钮（loading）
```

**C. 安装/向导（AppStore）**

```text
单 Modal 内 Steps（1 选版本 → 2 填参 → 3 确认风险）
每步校验；失败可回到上步；成功 Toast + 跳转已装列表
```

**D. Dashboard**

```text
首行：关键指标卡（大数字 + 趋势微色）
次行：图表（节流更新）
侧：今日待办 / 常用应用
点击指标卡 → 对应模块（便利跳转）
```

#### 18.3 交互感（克制动效）

- Hover：背景 `--fp-bg-hover`，150ms。
- Active：`scale(0.98)` 或 `translateY(1px)`，仅按钮。
- 页切换：opacity + 6px 位移，300ms；`prefers-reduced-motion` 关闭。
- 数字：可选轻量翻动，不阻塞。
- 禁止：整页视差、无限骨架闪烁、无意义的 Lottie。

#### 18.4 状态机（所有异步 UI 共用）

```text
idle → loading → success
              ↘ error（可 retry → loading）
空列表：success + empty，不是 error
```

组件：`FpTable` / `FpEmpty` / Skeleton；禁止只有转圈没有结构。

### 19. 美观与材质（现代面板）

#### 19.1 令牌（已有则补齐文档与缺口）

- 品牌：火焰橙 OKLCH（`--fp-brand*`）
- 表面：`--fp-bg-app` / `elevated` / `hover`
