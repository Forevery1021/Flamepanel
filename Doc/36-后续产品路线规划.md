## 1. 定位与原则

继续做 **复用 Linux 宿主机现有软件的轻量运维面板**，不转型 Kubernetes 控制台，也不重建另一套容器运行时。

从“有入口”转向“操作有证据、失败可解释、恢复可验证”：优先补齐既有网站、项目、备份、节点和任务中心的操作闭环，再考虑新的基础设施能力。代码已存在、自动化验证、真实系统验收、正式发布四种状态分开记录。

初始规划仅做维护与设计；后续 R-01 各片按用户单独确认的边界执行（§6）。Doc/30 的其他非目标仍有效，Doc/32 的历史周计划不作为自动开发清单。

## 3. 源码已有基础与仍需核验的差距

| 领域 | 现有入口 / 已知能力 | 下一轮先核验，不直接认定缺失 |

| 部署 | `application/project_service.rs`；部署策略、健康探测端口、路径校验；`project_ports.rs` | 各部署类型的失败补偿、并发部署、取消、重启中断及日志可解释性 |
| 恢复 | `application/backup_service.rs`；恢复前二次备份；备份账号与远端后端 | 独立环境恢复演练、远端不可用、校验失败、空间不足与恢复后业务可用性 |
| 节点 | `application/node_service.rs`、`agent/src/edge.rs`、`agent/src/heartbeat.rs` | 断连、旧版本协议、撤销凭据、时钟偏差与离线任务的真实行为 |
| 运维证据 | `MetricsHub`、历史指标、`TaskSupervisor`、任务 / 操作日志、通知 | 是否能从失败操作直达关联日志与节点、是否存在重复通知与敏感信息泄漏 |
| 安全自动化 | RBAC、MCP、审批、可选助手、`SecretCipher` | 审批后权限变化、工具目录权限过滤、凭据更新 / 密钥缺失边界 |
| 声明式配置 | `application/iac_service.rs` 的只读白名单 YAML 导出 | schema 版本与权限裁剪稳定性；当前明确没有导入 / 部署或完整恢复语义 |

以上是入口核对，不替代逐条黑盒验收。先建立能力 / 平台矩阵和失败用例，避免重复开发源码里已有的功能。

### P1：可恢复、可解释的操作闭环（P0 后优先）

| 切片 | 最小范围 | 依赖 / 风险 | 可验收结果 |
| --- | --- | --- | --- |
| R-01 恢复演练 | 先为 SQLite 面板备份制定隔离恢复验证工具与报告，再评估 UI；禁止覆盖生产目标 | 依赖现有备份格式、恢复前备份；临时目录 / 容量检查；外部数据库另分切片 | 正常、损坏、磁盘不足、远端失败四组；报告校验、恢复、启动、抽样读取阶段；记录实测 RTO / RPO，不先承诺固定数字 |
| R-02 部署失败保护 | 为一个已支持的部署类型补齐健康检查失败、超时、取消与回滚预检；首片不新增部署引擎 | 先确认现有策略与锁；镜像保留、配置和迁移兼容由人确认 | 健康失败时旧实例处理符合策略；重复操作不产生并发覆盖；明确显示代码与数据回滚边界 |
| R-03 统一故障追踪 | 复用任务 ID / request ID，把现有任务、节点、日志和通知关联；先一个部署场景 | 权限裁剪、日志脱敏；事件广播不是事务 Outbox | 用户从失败任务可定位原因与允许的重试入口；无权限时不泄漏路径 / 凭据；重试不重复执行已完成副作用 |

优先次序：R-01 → R-02 → R-03；每片单独确认、单独交付。遇到需要新 API 时同步权限、OpenAPI、生成类型与三语文案。

### P2：可靠节点与安全运维（依赖 P1 的任务证据）

| 切片 | 最小范围 | 验收条件与停止边界 |
| --- | --- | --- |
| N-01 节点能力与兼容矩阵 | 先盘点现有能力协商 / 版本信息；补充平台、运行时、权限与支持操作说明 | 旧 Agent、离线、鉴权撤销与重连用例；不支持操作拒绝并解释；不默默降级执行 |
| N-02 有界批量只读检查 | 先做节点体检聚合而非批量写操作；复用既有监控 / 任务 | 有并发和超时上限、取消、部分失败报告与逐节点权限检查；不引入新消息队列 |
| S-01 凭据生命周期 ADR | 区分历史明文兼容、密钥缺失、密钥轮换和持久化错误；先提出迁移 / 恢复方案 | 密钥轮换失败可恢复；现存密文不丢失；是否取消明文降级必须单独批准，不能混入去重 |
| S-02 审批与助手边界 | 复核现有 MCP 审批、执行时权限和工具目录，先加拒绝路径回归 | 审批后撤权、重复执行、过期审批与提示注入不绕过权限；AI 不获得任意 shell 或绕过审批能力 |

### P3：声明式能力与供应链（先 ADR 再代码）

- **I-01 只读 IaC 漂移预览提案**：以当前白名单导出为起点，先定义 schema 版本、稳定资源标识、秘密引用、缺失字段含义与权限裁剪。首片仅比较，绝不执行导入 / 部署。必须证明无秘密出现在差异和日志中。
- **A-01 应用升级预检提案**：复用已有应用生命周期，先展示磁盘 / 端口 / 依赖 / 备份条件；升级策略与数据迁移分开，补偿能力不足时不宣称自动回滚。
- **供应链发布 ADR**：评估签名、来源证据、SBOM 和固定镜像策略；实施可能涉及构建，**不属于本轮授权**，不得修改现有云原生构建。

继续暂缓：eBPF、QUIC、零信任网络、云镜像矩阵、PR 预览集群、自建 Kubernetes 管理面。需用户场景、威胁模型、运维成本和架构决策，不按竞品功能清单自动上马。

## 5. 每片开工模板

1. 真实用户问题与一条端到端成功路径。
2. 已有源码 / API / 权限 / 测试证据，以及确实缺失的部分。
3. 改动文件、禁改清单、数据 / 协议兼容、迁移与回退边界。
4. 正例、拒绝、超时、取消、重试、重启中断和权限变更的验收用例。
5. 云原生开发环境预算、测试命令、所需真实系统资源；无条件时明确未验证。
6. 接口变更同步 OpenAPI / 权限 / 类型 / i18n；新增事件需说明事务一致性。
7. 最终工作树与证据；推送、PR、云构建、发布分别授权。

不按未经测量的日历承诺上线日期。M-01 已有实现与回归，M-03 逐片持续执行；M-02 的 C02–C06 仍保留、待明确兼容决定，不因 R-01 推进而自动删除。当前已授权的 R-01 按 §6 与 Doc/41 小片交付；E-2 及后续必须先确认安全边界和真实资源，不再把已经选定 R-01 的决定当作待办。
