## 1. 项目与架构总览

### 1.1 项目定位

FlamePanel 是自托管服务器运维面板，对标 1Panel，核心能力包括：

- 系统监控（WebSocket 实时指标）
- Docker 全生命周期管理
- 多 Web 引擎（Nginx / Apache / OpenLiteSpeed / OpenResty / Caddy）
- 数据库 / 防火墙 / 文件 / 终端
- 应用商店（1Panel / 宝塔 / Flame 三格式；容器 / 原生 / WASM 三模式）
- JWT + RBAC（admin / operator / viewer，约 73 项权限）
- 节点 Agent（注册 / 心跳 / 远程命令）

### 1.2 技术栈

| 层面 | 技术 |
|------|------|
| 后端架构 | Clean Architecture + Hexagonal（domain → application → infrastructure → api） |
| 框架 | Rust + Axum |
| 数据库 | SQLite（sqlx）+ InMemory 双模式 |
| 认证 | jsonwebtoken + bcrypt |
| 容器 | Bollard |
| 插件 | wasmtime |
| 前端 | Vue 3 + OpenVue + Pinia + Vite |

### 1.3 分层职责

| 层 | 目录 | 职责 | 依赖约束 |
|----|------|------|----------|
| Domain | `domain/` | 实体、枚举、Repository trait、领域行为 | 零外部依赖 |
| Application | `application/` | Service 编排、端口定义 | 只依赖 domain / ports |
| Infrastructure | `infrastructure/` | SQLite / InMemory / Docker / OS 实现 | 实现 domain trait |
| API | `api/` | Handler、中间件、路由组合根 | 经 Service 调用 |
| 系统能力 | `plugin/` `webserver/` `database/` `firewall/` `terminal/` `event/` `resilience/` `utils/` | 独立能力模块 | 依赖 core |
| 运行时 | `runtime/`（目标态） | TaskSupervisor、request_id | core |

**核心规范（必须遵守）：**

1. `domain/` 不依赖 sqlx / axum / bollard。
2. Handler / Middleware **严禁**绕过 Service 直接访问 Repository。
3. Application 禁止直接 `use crate::infrastructure::具体类型`（应通过端口注入）。
4. 组合根：`FlameKernel::build_services` 组装 `Services`，`api/routes.rs` 汇聚路由。

### 1.4 请求链路（现状）

```
前端 → Nginx/Vite Proxy
    → RateLimiter（全局 Mutex）
    → Auth+RBAC 中间件（JWT 校验 + 查用户 + 权限检查）
    → Handler
    → Service
    → Repository / Docker / OS
    → JSON 响应
```

写操作额外：中间件异步 `tokio::spawn` 写审计日志。

### 1.5 已有优点

- 分层方向正确，Domain 较干净
- 认证 + RBAC 合并中间件（一次 JWT + 一次用户查询）
- 统一 `AppError` + 稳定错误码
- InMemory / SQLite 双模式利于测试
- 强制改密、登录锁定、路径沙箱、SQLite WAL 等安全基线已起步
- 路由规模大（约 150–180 条），功能面完整

## 2. 核心代码现状

### 2.1 组合根（`lib.rs`）

- `FlameKernel::build_services` 手动组装全部 Service（`Arc` 注入）
- 启动时 `tokio::spawn` 多个后台任务：
  - 内置应用种子 / WASM 恢复
  - 定时任务 tick（30s）
  - 自动备份（60s）
  - 节点离线扫描（30s）
  - metrics 采集
- `run()` 绑定 Axum Server，支持 Ctrl+C / SIGTERM，但后台任务未统一纳入取消体系

### 2.2 中间件（`api/middleware.rs`）

- 白名单路径跳过认证
- Bearer JWT 校验
- 查用户 → 强制改密拦截 → `route_permission` → RBAC
- 写操作异步审计

### 2.3 权限映射（`api/types.rs`）

- `route_permission(method, path)` 巨型 `match`
- 覆盖用户 / 节点 / 网站 / Docker / 插件 / Web 引擎等几乎全部路由
- 新增路由必须手工同步，否则易漏鉴权

### 2.4 Service 分页模式（问题主路径）

```rust
// 典型反模式（现状）
let items = self.xxx_repo.list_all().await?;
let total = items.len() as i64;
let data = paginate_slice(&items, params);
```

文档曾宣称分页下沉，但核心列表仍大量内存切片。

### 2.5 速率限制（`api/rate_limiter.rs`）

```rust
clients: Mutex<HashMap<String, RateEntry>>  // 全局锁 + 固定窗口
```

- 默认约 120 req/min（分级：Login 5 / Api 120 / Health 600；分片结构，Stage 3 已升级）
- IP 取自 `X-Forwarded-For`，易伪造
- 无登录/普通 API 分级

### 2.6 JWT / 密码

- JWT：HS 对称密钥，Claims 以 `sub` + `exp` 为主
- 密码：bcrypt DEFAULT_COST
- 中间件路径上存在重复构造 `JwtUtils` 的可能

### 2.7 仓储工厂（`infrastructure/factory.rs`）

- `RepoFactory` 按 InMemory / SQLite 创建各 Repository
- Docker 可选 Bollard，失败回退 InMemory
- 模式清晰，利于测试

## 3. 架构问题分析

| ID | 问题 | 表现 | 影响 | 优先级 |
|----|------|------|------|--------|
| A1 | 分页未真正下沉 | Service `list_all` + 内存切片 | 数据增大后内存/CPU 线性恶化 | P0 |
| A2 | 权限巨型 match | 单函数覆盖全部路由 | 扩展易漏鉴权，维护成本高 | P0 |
| A3 | 后台任务裸 spawn | 无统一 CancellationToken/JoinSet | 优雅关闭不完整，可能残留写库 | P0 |
| A4 | 鉴权无短缓存 | 每请求查用户/可能查权限 | 鉴权路径 DB 压力大 | P0 |
| A5 | 上帝 trait | `DockerRepository` 方法过多 | 实现/测试/演进困难 | P1 |
| A6 | 错误映射粗糙 | sqlx 错误多落到 Internal | 前端只能看到 500 | P1 |
| A7 | 事件 fire-and-forget | `let _ = publish(...)` | 审计/通知可能丢 | P2 |
| A8 | AppState 过大 | 字段 20+，手动组装 | 可测性与演进成本上升 | P2 |

### 3.1 A1 详解：分页

影响模块（最低集）：

- `UserService`
- `NodeService`
- `WebsiteService`
- `OperationLogService`
- `LogService`
- `ScheduledTaskService`

正确方向：Repository 提供 `list_page(limit, offset)` + `count()`，Service 只做参数校验与组装。

### 3.2 A2 详解：权限映射

`route_permission` 用 `starts_with` / `ends_with` 拼路径规则，Docker/Plugin 细粒度动作尤其脆弱。

目标态：

- 路由定义时声明 `(resource, action)`
- 未声明权限的受保护路径 **默认 403**（拒绝比放行更安全）

### 3.3 A3 详解：任务生命周期

必须纳入 Supervisor 的任务：

- metrics 采集
- scheduled_task tick
- auto backup
- node offline scanner
- event subscription loop

关闭时：cancel → 等待（如 5s）→ 超时 abort。

### 3.4 A4 详解：鉴权缓存

缓存对象：

- `user_id → User`（TTL 10–30s）
- `role → permissions`（TTL 30–60s）

失效点：

- 用户更新 / 删除 / 改角色 / 改密
- 角色权限变更

中间件仍只调 Service，不直接碰缓存实现（保分层）。

## 4. 性能开销分析

### 4.1 热路径成本（单次受保护请求）

| 环节 | 现状开销 | 严重度 | 说明 |
|------|----------|--------|------|
| RateLimiter | 全局 Mutex | 中 | 高并发串行化 |
| JWT | decode + 可能重复 new | 低–中 | 可复用实例 |
| 用户查询 | 每次 DB | **高** | 无缓存 |
| RBAC | 可能再次查库 | 中–高 | 无角色权限缓存 |
| 业务列表 | 全量加载 | **高** | 内存分页 |
| 审计 | 异步 spawn | 低 | 不阻塞，但任务多 |

### 4.2 后台任务开销

- 节点离线扫描：全量 `list_nodes` 再过滤（应改为按 `last_heartbeat_at` 条件查）
- 自动备份：每 60s 读 settings 再决定
- metrics：周期性 sysinfo 全量采集（可接受，注意锁竞争）

### 4.3 其他

- `AppState` 频繁 Clone（大量 Arc，成本可控但可收敛）
- broadcast 事件通道固定容量，高频时可能丢消息
- SQLite 已 WAL，但审计 + 心跳 + 备份并发写仍可能 busy

### 4.4 优化收益预期

| 改造 | 预期收益 |
|------|----------|
| 分页下沉 | 列表接口 CPU/内存从 O(n) 降为 O(page) |
| 鉴权缓存 | 鉴权 DB 往返显著下降 |
| 限流升级 | 去掉请求入口全局锁 |
| Supervisor | 关闭可预期，无僵尸任务 |
| 离线扫描条件查询 | 节点规模上升后仍可用 |

## 5. 改造目标与原则

### 5.1 目标

1. **正确性**：分页、权限、关闭路径行为可测且稳定
2. **性能**：去掉列表全表加载与鉴权重复查库
3. **安全**：未声明权限默认拒绝；限流与 JWT 更严谨
4. **可维护**：权限与路由绑定，任务生命周期统一

### 5.2 原则

1. 小步提交，一 Stage 一 PR
2. 先测后改，改后回归
3. 不绕过 Service
4. 不引入新的 `list_all + 内存分页` 主路径
5. 生产默认只增强安全/性能，不削弱校验
6. 同步更新 `Doc/` 与 `CHANGELOG.md`

### 5.3 总验收门槛

- [ ] `cargo test --all` 全绿
- [ ] `cargo clippy --all-targets -- -D warnings` 0 warning
- [ ] 分页 / 鉴权缓存失效 / 429 / 优雅关闭有测试
- [ ] 新路由有权限声明
- [ ] 关闭后 5s 内后台任务退出

### Stage 1：真正分页下沉（P0，A1）

#### 1.1 Domain 契约

```rust
#[async_trait]
pub trait UserRepository: Send + Sync {
    // 保留原有方法
    async fn list_page(&self, limit: i64, offset: i64) -> Result<Vec<User>, AppError>;
    async fn count(&self) -> Result<i64, AppError>;
}
```

同样扩展：`NodeRepository`、`WebsiteRepository`、`OperationLogRepository`、`LogRepository`、`ScheduledTaskRepository` 等列表型仓储。

规则：`limit` 在仓储或 Service 层 clamp 到 `1..=200`。

#### 1.2 SQLite 实现示例

```rust
async fn list_page(&self, limit: i64, offset: i64) -> Result<Vec<User>, AppError> {
    let limit = limit.clamp(1, 200);
    let rows = sqlx::query_as::<_, UserRow>(
        "SELECT * FROM users ORDER BY id DESC LIMIT ? OFFSET ?"
    )
    .bind(limit)
    .bind(offset)
    .fetch_all(&self.pool)
    .await?;
    Ok(rows.into_iter().map(Into::into).collect())
}

async fn count(&self) -> Result<i64, AppError> {
    let (c,): (i64,) = sqlx::query_as("SELECT COUNT(*) FROM users")
        .fetch_one(&self.pool)
        .await?;
    Ok(c)
}
```

InMemory：对 Vec 切片 + `len()`，双模式行为一致。

#### 1.3 Service 改造

**禁止：**

```rust
let all = self.user_repo.list().await?;
let data = paginate_slice(&all, params);
```

**改为：**

```rust
pub async fn list_users_paginated(
    &self,
    params: &PaginationParams,
) -> Result<PaginatedResponse<User>, AppError> {
    let limit = params.limit.clamp(1, 200) as i64;
    let offset = ((params.page.max(1) - 1) as i64) * limit;
    let total = self.user_repo.count().await?;
    let data = self.user_repo.list_page(limit, offset).await?;
    Ok(PaginatedResponse::new(data, total, params))
}
```

#### 1.4 测试

- 插入 100+ 条；`page=2&limit=10` → `data.len()==10` 且 `total` 正确
- mock 断言调用 `list_page`，不调用全量 `list`

**验收：** 主列表路径无内存分页；双后端实现齐全；测试通过。

> ✅ **已落地（PR #35）**：User/Node/Website/WebServer/Database/Firewall/Settings 七个仓储新增 `list_page` + `count`（SQLite `LIMIT/OFFSET`、InMemory 倒序切片），7 个 Service 分页全部改为调用仓储，移除 `list_all + paginate_slice` 主路径；离线扫描条件化（`list_stale_heartbeats`）；新增 3 分页单测。

### Stage 6：错误映射细化（P1，A6）

```rust
impl From<sqlx::Error> for AppError {
    fn from(e: sqlx::Error) -> Self {
        match &e {
            sqlx::Error::RowNotFound => {
                AppError::NotFound("Resource not found".into())
            }
            sqlx::Error::Database(db) if db.is_unique_violation() => {
                AppError::Conflict("Resource already exists".into())
            }
            _ => AppError::internal_with_source("Database operation failed", e),
        }
    }
}
```

> required exp+sub）；`rotate_secret` 同步替换共享实例使旧令牌立即可失效；新增 5 例单测。

1. `AppState` 持有 `Arc<JwtUtils>`，禁止每次请求 new
2. 显式 Validation：

```rust
let mut v = Validation::new(Algorithm::HS256);

v.leeway = 30;

```

3. 可选：Claims 增加 `typ` / `jti`；refresh 旋转

**验收：** 算法受限；实例复用；密钥长度启动校验仍在。

## 9. 禁止事项与回滚策略

### 9.1 禁止

1. Handler / Middleware 直接访问 Repository
2. 新增 `list_all + paginate_slice` 业务主路径
3. 未声明权限的受保护路由默认放行
4. 生产路径对可恢复错误使用 `unwrap` / `expect`
5. 向客户端返回内部 source 错误链

### 10.3 最小可用补丁（优先收益）

**Repository：**

```rust
async fn list_page(&self, limit: i64, offset: i64) -> Result<Vec<User>, AppError>;
async fn count(&self) -> Result<i64, AppError>;
```

**Service：**

```rust
let limit = params.limit.clamp(1, 200) as i64;
let offset = ((params.page.max(1) - 1) as i64) * limit;
let total = self.user_repo.count().await?;
let data = self.user_repo.list_page(limit, offset).await?;
```

**缓存入口：**

```rust
pub async fn find_by_id(&self, id: i64) -> Result<Option<User>, AppError> {
    if let Some(u) = self.cache.users.get(&id).await {
        return Ok(Some(u));
    }
    let u = self.user_repo.find_by_id(id).await?;
    if let Some(ref user) = u {
        self.cache.users.insert(id, user.clone()).await;
    }
    Ok(u)
}
```
