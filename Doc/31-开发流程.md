# 31 · 开发流程

> 人类与 AI 使用同一套范围、代码红线和验收。核心架构见 [Doc/01](./01-架构设计.md)，当前维护方向见 [Doc/30](./30-路线图与里程碑.md)，工序细节见 [Skills](../.codebuddy/skills/)。历史交付不重复堆进入口文档。

## 1. 一次交付

明确需求与禁改 → 检查现有实现 → 列计划和文件 → 小片实现 → 定点回归 → CNB 完整门禁 → Review / 审查包 → 授权合并或发布。

- 有指定 Issue 就把计划、风险和文件清单写入 Issue；没有编号不虚构 `Ref`。
- 功能、重构、依赖升级不要混片；同一冲突域串行。
- 范围外问题记录为清单，不顺手实现。清理先列 [Doc/35](./35-工程清理清单.md)，未经批准不删除运行时代码。
- 结果必须说明最终源码基线、dirty 状态、实际检查和未执行项目；不能把初始基线结果套到最终工作树。

## 2. 任务切片

按可独立验收的行为切，不按 domain → repo → service → API 分成无法独立验证的任务。

| 类型         | 范围                                            | 工序卡                                            |
| ------------ | ----------------------------------------------- | ------------------------------------------------- |
| A · 后端用例 | 领域 / 仓储双实现 / Service / API / 权限 / 测试 | backend-module + sqlite-migration + rest-endpoint |
| B · 后端增量 | 现有域的小修复、校验或接口变更                  | rest-endpoint / sqlite-migration                  |
| C · 前端     | API / composable / view / Fp 组件 / i18n / spec | frontend-view                                     |
| D · 工程维护 | 测试装配、工具链、文档、构建或拆分              | quality-gates                                     |

性能先建立可重复基线；拆分保持签名、行为与数据格式，不把已有模块化工作重新列作“待拆”。

## 3. Issue 模板

```markdown
## 背景与目标

为什么做；一句话可验收目标；对应维护 / 路线条目。

## 范围

基线 commit；按序读取的文件 / 符号；允许修改文件；明确禁改项。

## 风险

权限、协议、旧数据、外部 API、feature、默认行为与回滚。

## 验收

定点成功 / 失败路径；完整门禁；至少一项可机器判定标准。

## 交付

真实命令与结果；锁文件差异；文档同步；未解决项 / 后续建议。
```

任务路径失效时指出差异后按源码继续，不猜接口或复制旧行号。计划行号必须注明基线；长期文档优先使用路径 + 符号。

## 4. 分支、提交与外部操作

- 从当前 main 建工作分支：`fix|refactor|docs|chore/<issue-or-scope>`；不直推 main，不强推共享历史。
- 中文 Conventional Commits：`类型: 描述`；有真实 Issue 才附 `(Ref: #<issue>)`。
- 审查描述五节：关联需求 / 变更清单 / 实现说明 / 测试结果 / 后续建议；结果不夸大未执行的检查。
- 提交不含令牌、私钥、`target/`、`node_modules/`、`dist/` 等生成物。
- 推送、PR、tag、发布是外部操作，不是测试的前置条件；用户限制构建额度时先交付工作分支 / patch 和审查报告。

## 5. 门禁与执行环境

### 5.1 统一入口

```bash
bash scripts/ci-local.sh --help
bash scripts/ci-local.sh quick
bash scripts/ci-local.sh --keep-going all
```

命令与分组由 `ci-local.sh` 维护，不在每份文档再复制 cargo / npm 检查列表。

- Rust 相关组首先验证精确工具链；构建 / 测试保留 `--locked` 和既有 feature 范围。
- frontend 使用 `npm ci`；覆盖率与包体预算查实际配置，不根据历史报告降阈值。
- `all` 含真实 SQLite 后端的 Chromium E2E，但不含 perf、Rust cargo-audit、完整 release 架构矩阵或真机安装 / 多节点验收。
- 定点回归不能代替完整门禁；门禁通过也不能代替未覆盖的验收层。

### 5.2 环境与额度

| 环境               | 用途                               | 注意                                           |
| ------------------ | ---------------------------------- | ---------------------------------------------- |
| 工作副本           | 编辑、diff、源码与文档分析         | 不据静态检索直接删代码                         |
| **CNB 云原生开发** | 本项目开发 / 测试与完整 `ci-local` | 使用开发额度；内部复用构建引擎不等于普通云构建 |
| CNB 普通流水线     | 按仓库事件配置执行门禁 / 发布      | 轻量安装回归仍消耗构建额度，不是“约等于免费”   |
| GitHub Actions     | 镜像门禁、审计与发布流程           | 不因为有配置就宣称本轮已经运行                 |

额度以账号实际方案和账单为准，不在文档写死。用户要求**不使用云构建时长**时，禁止用普通 build-start、push / PR / tag 验证；push CI skip 不覆盖 PR 事件。

### 5.3 云原生开发操作与证据

`cnb-workspace.sh` 提供 start / sync / bg / hold / log / stop；使用前检查令牌权限和目录约定。令牌仅进入授权的临时进程 / 环境，不写文件、Git URL 或日志。

- 每条 SSH 连接先校验 `cnb.space` 的 RSA 公钥 SHA-256 指纹，再启用 strict checking；固定值与更新依据见脚本及 [CNB 官方指纹公告](https://docs.cnb.cool/zh/workspaces/fingerprint.html)。只使用 RSA/SHA-2 签名，不回退 SHA-1 或 TOFU。
- 使用独立 0700 临时目录和 0600 `known_hosts`，不读取 / 改写用户的信任文件；连接退出后清理。获取失败、空结果、指纹不符、混入未知 key、非官方目标及异常输入均拒绝连接，不提供环境变量绕过。
- 当前脚本仅支持官方 `cnb.space` 目标。官方轮换指纹或接入其他 SSH 主机时，须先核实可信来源并单独评审更新；不得临时切回 `accept-new` / `StrictHostKeyChecking=no`。
- 离线回归：`python3 scripts/tests/test_cnb_workspace.py`，用替身验证全部 SSH 入口，不启动真实工作区或普通流水线。

执行顺序：

1. 启动或复用开发实例，等 workspace ready；SSH 使用官方指纹核验的 known-hosts。
2. 同步**最终工作树**（包含未提交变更），而不是只 `git archive HEAD`；在自有隔离目录执行。
3. 不覆盖 `/workspace`：它可能恢复了别人的未提交工作。隔离目录与编译缓存不保证跨实例持久化。
4. 长任务保持前台 SSH 连接或 `hold`；后台进程本身不保证保活。不要为防回收长期调高 idle timeout。
5. 保存 revision / dirty 标记、源码摘要、实际 Rust / Node / npm、CPU / 内存、逐项 PASS / FAIL / 时间、完整日志和覆盖率等报告。
6. 下载证据后停止该实例，并确认停止结果；不把目录存在或进程启动当作任务完成。

小内存环境不要并行 Rust 大 crate 与 vite；优先使用已定义 feature 子集。不要为通过门禁修改 profile / RUSTFLAGS / 质量阈值。

## 6. Review 六看

1. **范围**：实际 diff 是否包含未授权的功能、重构或删除？
2. **契约**：真实调用、公开接口、生成类型、错误与数据格式是否保持？
3. **权限**：路由 / PermissionRule / 401、403 / 前端权限是否一致？
4. **状态**：迁移、旧数据、seed、缓存失效、取消 / 关闭是否可回归？
5. **测试真实性**：装配真实、断言独立、失败路径有效，是否偷偷 skip / 静音？
6. **证据**：最终工作树、环境、检查结果、锁文件、现存警告和未验证部分是否清楚？

反馈一次列全，定位到文件 + 符号 + 期望行为；范围外发现写后续清单。

## 7. 文档同步矩阵

| 修改                     | 同步                                                                |
| ------------------------ | ------------------------------------------------------------------- |
| API / DTO                | 注解、OpenAPI 注册 / 快照、生成 API 文档与类型；Doc/02 保留场景解释 |
| 表 / 索引 / 迁移         | Doc/03，幂等迁移回归                                                |
| 权限                     | `api/permissions.rs`、Doc/07、前端权限与否定用例                    |
| 配置 / 脚本 / 部署       | Doc/10、`.env.example` 等相关模板                                   |
| CLI / Agent / 事件       | 命令 catalog / Doc/10；Doc/23；Doc/24                               |
| 核心边界 / 工具链 / 清理 | Doc/01、AGENTS、Doc/35、对应 Skill                                  |
| 已交付 / 发布            | CHANGELOG、Doc/30 当前状态；历史执行记录放 Doc/32                   |

### 7.1 同步原则

源码优先；完成状态必须有实现 / 测试证据。长期文档不复制测试数、包体实测或依赖版本清单；精确结果进入一次性交付报告。

合并后检查受影响文档即可，不为了“同步”自动创建第二个会触发构建的 PR。若需独立文档 PR，先确认授权与额度。

## 8. 发布

发布是单独授权的动作，不属于当前清理：最终门禁 → 必要性能 / 安全审计 → 兼容矩阵与真机安装 / 多节点验证 → 对齐产品版本 → Release / tag / 镜像 → 记录产物与回滚。

工具链升级也单独成片：同步 rust-toolchain、workspace 最低支持声明、Docker / NPC / CI；只有明确需要才最小更新依赖锁文件，并补完整 feature / 发布目标验证。编译器固定不代表基础镜像或系统包已完全可复现。

## 9. AI 开发者约定

- 先计划、查现有调用，再实现；没有明确目标时问，不从历史路线图擅自加功能。
- 不伪造路径、Issue、测试、费用或发布状态；同一错误三轮止损。
- 文档精简以保留核心边界和操作为目标，不删除安全 / 兼容信息。
- 收尾交付代码 / 文档、真实报告、待批准清单；没有推送就明确说没有推送。
